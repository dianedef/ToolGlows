# Bug Record: BUG-2026-09-04-001

## Summary

- Current status: `fixed-pending-verify`
- Severity: `critical`
- Expected behavior: only internal extension contexts can invoke privileged background handlers.
- Observed behavior: every matched page receives an unlocked window bridge, while the background accepts its messages without checking the sender context.

## Root-cause hypothesis

`allowWindowMessaging` was treated as namespace isolation rather than as an opt-in page trust boundary. The extension has no maintained window-context client, so the gateway is unnecessary. Missing authoritative sender checks then turn that unnecessary gateway into privileged reachability.

## Fix applied

- Removed the page-world bridge opt-in.
- Added an authoritative internal-sender guard to every background bridge handler.
- Normalized settings and active-tool payloads before persistence or broadcast.
- Added source-level and browser-level hostile-sender regressions.
- Reused the tested reload implementation, bounded stalled reloads, and reported failures truthfully.
- Redacted sensitive diagnostic payloads, repaired missing UI favicon assets, and removed corroborated prototype residue.

## Retest history

- `vue-tsc --noEmit`: passed.
- `vitest run`: 39 files and 197 tests passed.
- Chrome and Firefox production builds: passed.
- `web-ext lint`: 0 errors and 12 known warnings.
- Hostile page bridge probe: `pageBridgeAccepted: false`.
- ShipGlows isolated Chromium lab: extension loaded, service worker observed, popup opened, no popup errors.
- `git diff --check`: passed; only repository line-ending notices were emitted.

The technical repair is verified locally. The record remains `fixed-pending-verify` because delivery and independent review were deliberately excluded from this shared dirty worktree operation.

## Approved repair scope

- Remove page-window messaging and add defense-in-depth sender validation to every background bridge handler.
- Normalize settings and tool identifiers at the background boundary.
- Make the tested reload implementation the production implementation and report dispatch failures truthfully.
- Remove sensitive production logs, repair missing UI assets, and delete only corroborated prototype residue.
- Retest typecheck, unit behavior, both browser builds, manifest lint, and an isolated MV3 load.
