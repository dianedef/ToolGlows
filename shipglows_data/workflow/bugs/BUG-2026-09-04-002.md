# Bug Record: BUG-2026-09-04-002

## Reproduction

Load the generated Chrome extension into an isolated Chromium profile. Open
https://fr.wikipedia.org/wiki/France, expand ToolGlows and click Mode sombre.
Measure elapsed time from the actual click event to the first observed active
button state; inspect the rendered page and toggle back off.

Expected: the page and toolbar respond promptly while retaining readable colors.
Observed: active state arrived after 5703 ms on Wikipedia, versus 395–560 ms on
example.com. A second pre-fix Wikipedia run measured 3797 ms. These are local
observations, not a hardware-independent latency guarantee.

## Diagnosis and fix attempt

2026-09-04 UTC: contrast repair and bright-surface softening interleaved
getComputedStyle reads with inline color or selector-attribute writes for each
element. On long pages each next read can force style recalculation. Contrast
repair also repeatedly reads shared ancestors' backgrounds.

The first attempt only grouped reads and writes; browser retest still showed multi-second stalls. The final bounded repair schedules refinements in cancellable batches (50 elements / 5 ms of planning, with 16 ms yields), collects changes before applying DOM writes and caches
ancestor background colors for each contrast pass. Existing exclusions,
hydration scans, theme values and stop/restore behavior remain in force.
An identical active-theme echo from the background now reuses the engine. No permissions, dependency versions or message contracts change.

## Proof plan

- Regression: activation performs no synchronous contrast scan; each batch reads before writing; cancellation clears pending work; duplicate themes do not re-enable the engine.
- Existing contrast, dynamic content, bootstrap and lifecycle tests.
- Typecheck, complete unit suite, both browser builds and Firefox manifest lint.
- Real Wikipedia and example.com activation/deactivation using the built extension.
- Human visual acceptance remains pending after agent browser inspection.

## Targeted BackerKit adaptation — 2026-09-05

Source and browser diagnosis establish two independent causes. The embedded
DarkReader default fetcher rejects external resources; normal page CORS fetches
also fail for BackerKit's two CDN stylesheets and background JPEG. Separately,
surface rescans read their own dark override and remove its marker, reverting
the container to white. Both weaknesses also exist in historical `4687e9a`.
A representative isolated fixture using the public BackerKit styles reproduced
white at about 767 ms, dark at 790 ms, white again at 942 ms, and white with no
surface marker at 6.5 seconds. This is a focused fixture, not full-site proof.

Implemented a dedicated anonymous CSS/image fetch adapter through the existing
internal bridge and host permissions, with validated content-script tab/frame,
URL restrictions, no credentials/referrer/redirects, MIME restrictions, timeout,
stream size and concurrency bounds. No manifest permission was added. Surface
roles now remain stable until disable removes them. Historical engine/backdrop
mechanisms and existing dirty work are preserved; no broad rollback performed.

Technical proof: five focused files / 28 tests passed initially; the resource
adapter, bridge constraints and real computed-style rescan/disable regression
then passed in three files / 17 tests. Typecheck passed before final queue-only
adapter changes. Browser builds and post-fix rendering proof remain owned by
the integration run. Keep this issue fix-attempted pending that retest and
human acceptance; technical tests alone do not establish visual resolution.
